# Supply chain assurance

How a Duckle release is built, what is published alongside it, and what a
consumer can verify without trusting the release page.

---

## 1. What ships with every release

| Artifact | What it answers |
| :--- | :--- |
| The binaries | - |
| `SHA256SUMS.txt` | Was this download altered in transit? |
| `duckle-sbom.cdx.json` | What is actually inside this build? |
| Build provenance attestation | Who built it, from which commit, on what workflow? |
| `capabilities.json` | What can this exact version do? |

The three verification artifacts answer different questions and none of them
substitutes for another. A checksum file proves a download matches what the
release page says; it proves nothing about where the release page's contents
came from, because an attacker who can replace a binary can replace the sums
file beside it. That gap is what provenance closes.

---

## 2. Provenance

Every published binary, the checksums file and the SBOM carry a build
provenance attestation, generated by `actions/attest-build-provenance` and
signed keylessly through Sigstore using the release workflow's own short-lived
OIDC identity. There is no signing key for Duckle to hold, rotate or lose.

Verify a download against the repository that is supposed to have produced it:

```bash
gh attestation verify Duckle-linux-x64 --repo slothflowlabs/duckle
```

That checks the artifact's digest against a signed statement naming the source
repository, the commit and the workflow run that produced it. A binary built
somewhere else fails, even if someone also replaced `SHA256SUMS.txt`.

### What this is not

**This is not code signing.** Authenticode on Windows and notarization on macOS
require a purchased certificate tied to a verified legal entity, and Duckle does
not have one yet - an unsigned build still shows the operating system's
unrecognised-publisher warning. Provenance and code signing solve different
problems: one tells you where an artifact came from, the other tells the
operating system to run it without complaint. Provenance is available today at
no cost and is the one that answers the supply-chain question.

## 3. Software bill of materials

`duckle-sbom.cdx.json` is a CycloneDX document covering the Rust workspace and
the frontend, generated from the committed lockfiles at release time. It exists
so a deployment can answer "does the version we installed contain this crate?"
against the artifact in front of them, rather than against whatever the
repository happens to look like when the question is asked - which is a
different answer as soon as one release has gone by.

The SBOM is regenerated and checked on every push, not only at release, so it
cannot quietly stop building. That check also fails if the generator produces an
implausibly small document, because a green tick on an empty file is worse than
no file.

---

## 4. Dependency scanning

`cargo audit` over `Cargo.lock` and `npm audit` over `package-lock.json`, in the
`supply-chain` workflow, on every push and pull request **and weekly on a
schedule**.

The schedule is not redundant with the push trigger. A vulnerability is normally
published against a dependency that is already shipping, months after the commit
that introduced it - so a scanner wired only to pushes reports nothing until
somebody happens to touch the tree, and reports it as though it were new.

Advisories with no upstream fix are listed in `.cargo/audit.toml`, each pointing
at a section of [Dependency advisories](../reference/dependency-advisories.md)
recording its reachability and what would let the entry be removed. Every other
advisory fails the build. The list carries a review date, because "no fix
available yet" is a statement that ages.

---

## 5. Build integrity

* **Lockfiles are committed**, so a build resolves the same dependency graph a
  scan was run against. A release cannot pick up a version nothing checked.
* **Releases are built only by the release workflow**, from a tag, on hosted
  runners. Provenance makes that checkable rather than merely stated.
* **Binaries are verified before publication.** The release workflow refuses to
  publish a Linux binary that has picked up a `libodbc.so` dependency, and
  refuses a desktop build whose frontend is not embedded - two regressions that
  previously reached users.
* **The in-app updater verifies before swapping.** A downloaded build is checked
  against the published `SHA256SUMS.txt` before it replaces the running binary.

---

## 6. What is not covered

Stated plainly, because a supply chain document that only lists strengths is not
useful to anyone assessing one:

* **No code signing certificate.** See section 2.
* **No reproducible builds.** Two runs of the release workflow on the same
  commit are not guaranteed to be bit-identical. Provenance says where a binary
  came from; it does not let a third party rebuild it and compare.
* **Vendored DuckDB CLI binaries** are checked into the repository. They are
  vendored deliberately, and they are outside the SBOM's dependency resolution.
